# Event Schema (v1)

**Status:** authoritative. Code follows this document. If the design is wrong,
change this file first and say why, then change the code.

Implementation lives in `shared/src/index.ts`.

---

## 1. Design principles

1. **Append-only.** Events are facts that happened. They are never updated or
   deleted. Run-level aggregates are derived by summing events.
2. **Closed event set.** Nine types, listed in §3. A tenth type is a v2
   conversation, not a quick addition. A closed set is what makes the timeline
   renderable and the dashboard legible.
3. **`seq` orders, `timestamp` displays.** The SDK assigns a monotonic `seq` per
   run starting at 0. Batches can arrive out of order or be retried; `seq` is
   the only ordering authority and the dedup key. Timestamps come from the host
   machine and are used for timeline x-position only.
4. **Payloads are opaque JSON to the collector.** The collector validates the
   envelope strictly and the payload loosely. This is deliberate: agent payloads
   vary wildly across frameworks, and a strict payload schema would make the SDK
   brittle at exactly the moment a user is trying to debug something weird.
5. **Cost is recorded, not computed.** The SDK reports `costUsd` if it knows it.
   The collector does not maintain a pricing table. Pricing tables go stale and
   silently produce wrong numbers, which is worse than no number.

---

## 2. Envelope

Every event, regardless of type, has this envelope:

| Field | Type | Required | Notes |
|---|---|---|---|
| `seq` | int >= 0 | yes | Monotonic per run, assigned by SDK, starts at 0 |
| `type` | EventType | yes | One of the nine in §3 |
| `timestamp` | ISO 8601 string | yes | Host clock, UTC |
| `durationMs` | int >= 0 | no | For events that span time (llm_call, tool_call) |
| `payload` | JSON object | yes | Type-specific, see §3. May be `{}` |
| `tokensIn` | int >= 0 | no | |
| `tokensOut` | int >= 0 | no | |
| `costUsd` | number >= 0 | no | Reported by caller, never computed by collector |

Unknown envelope fields are **rejected** (`.strict()`). Unknown *payload* fields
are **kept**. That asymmetry is the point of principle 4.

## 3. Event types

| Type | Meaning | Expected payload keys (all optional) |
|---|---|---|
| `run_start` | Run began | `agentName`, `model`, `metadata` |
| `llm_call` | Request sent to a model | `model`, `messages`, `temperature`, `tools` |
| `llm_response` | Model responded | `content`, `finishReason`, `toolCalls` |
| `tool_call` | Agent invoked a tool | `toolName`, `args`, `callId` |
| `tool_result` | Tool returned | `toolName`, `callId`, `result`, `ok` (bool) |
| `retry` | An operation was retried | `attempt` (int), `reason`, `ofSeq` (int) |
| `error` | Something failed | `message`, `stack`, `fatal` (bool) |
| `agent_decision` | Agent chose a branch | `decision`, `reasoning`, `options` |
| `run_end` | Run finished | `status` (completed \| failed), `summary` |

**Pairing.** `tool_call` / `tool_result` pair on `callId`. `llm_call` /
`llm_response` pair on adjacency. The dashboard uses pairing to draw spans
rather than points on the timeline. Unpaired events render as points, which is
itself a useful debugging signal (a `tool_call` with no `tool_result` is
visibly a hang).

---

## 4. Payload truncation

LLM payloads bloat SQLite fast. A single agent run can carry megabytes of
message history that nobody will ever scrub through.

**Rule:** the SDK serializes the payload; if the JSON string exceeds **50 KB**,
it replaces the payload with:

```json
{ "_truncated": true, "_originalBytes": 184320, "_preview": "<first 2000 chars>" }
```

Truncation happens **in the SDK**, before the network call. Rationale: the goal
is to protect the user's bandwidth and the collector's disk, and truncating at
the collector protects neither. The dashboard renders `_truncated` payloads with
an explicit badge so a truncated payload is never mistaken for a small one.

Full-fidelity storage with blob offloading is v2.

## 5. Storage

### `runs`

| Column | Type | Notes |
|---|---|---|
| `id` | TEXT PK | uuid v4, generated by SDK |
| `name` | TEXT NOT NULL | |
| `agent_name` | TEXT | |
| `model` | TEXT | |
| `started_at` | TEXT NOT NULL | ISO 8601 |
| `ended_at` | TEXT | NULL while running |
| `status` | TEXT NOT NULL | `running` \| `completed` \| `failed` |
| `total_tokens_in` | INTEGER DEFAULT 0 | derived |
| `total_tokens_out` | INTEGER DEFAULT 0 | derived |
| `total_cost_usd` | REAL DEFAULT 0 | derived |
| `metadata` | TEXT | JSON |

### `events`

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `run_id` | TEXT NOT NULL | FK -> runs(id) ON DELETE CASCADE |
| `seq` | INTEGER NOT NULL | |
| `timestamp` | TEXT NOT NULL | |
| `type` | TEXT NOT NULL | |
| `duration_ms` | INTEGER | |
| `payload` | TEXT NOT NULL | JSON |
| `tokens_in` | INTEGER | |
| `tokens_out` | INTEGER | |
| `cost_usd` | REAL | |

**Indexes and constraints:**

```sql
CREATE UNIQUE INDEX idx_events_run_seq ON events(run_id, seq);
CREATE INDEX idx_runs_started_at ON runs(started_at DESC);
```

The unique index on `(run_id, seq)` is load-bearing: it makes batch retries
idempotent. The insert path uses `INSERT OR IGNORE`, so a re-sent batch after a
timeout is a no-op rather than a duplicate. This is the mechanism that lets the
SDK retry safely without any coordination.

**Derived totals** are recomputed on the `runs` row inside the same transaction
as the event insert, summed from the `events` table. Never incremented blindly
from the batch, or a retry would double-count.

Run in WAL mode with `foreign_keys = ON`.

## 6. API

| Method | Path | Body | Returns |
|---|---|---|---|
| `GET` | `/health` | - | `{ status: "ok" }` |
| `POST` | `/runs` | run metadata | `{ id }` |
| `POST` | `/runs/:id/events` | `{ events: Event[] }` (batch, max 500) | `{ accepted, skipped }` |
| `PATCH` | `/runs/:id` | `{ status, endedAt }` | `{ ok: true }` |
| `GET` | `/runs` | - | paginated run summaries, newest first |
| `GET` | `/runs/:id` | - | run + derived totals |
| `GET` | `/runs/:id/events` | `?after=<seq>&limit=<n>` | events ordered by `seq` |

**Error contract:** `400` with `{ error, issues }` for Zod failures (pass the
flattened Zod issues straight through - they are genuinely good error messages).
`404` for unknown run. `413` for a batch over the size cap. Never `500` for
anything caller-caused.

`skipped` in the batch response counts events rejected by the unique index, i.e.
duplicates from a retry. It is not an error. The dashboard ignores it; it exists
so the SDK can log it in debug mode.

## 7. Open questions (decide before implementing, do not silently guess)

1. **Decided (0.2):** `POST /runs` creates the row, and the SDK also emits a
   `run_start` event at `seq: 0`. Redundant by design - event sourcing wants the
   event log alone to be a complete record, not dependent on the `runs` row.
   Does not change the shape of the `run_start` schema, only how the collector
   calls it in 1.1 - noted here so that task doesn't re-litigate it.
2. **Deferred, not decided:** whether `seq` gaps should be surfaced in the
   dashboard. Explicitly depends on the dashboard existing (Phase 2). Nothing in
   the 0.2 schema work forecloses this - a gap is just a hole in the `seq`
   sequence, detectable later from stored events without any schema change.
